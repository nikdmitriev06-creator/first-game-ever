# Структура проекта

Куда класть файлы. Новые скрипты остаются в глобальном пространстве имён: у MonoBehaviour идентификатор Unity — это имя класса без namespace.

Уже появились папки `Core`, `Interaction`, `Inventory`. Старые скрипты из `Player`, `Items`, `World`, `Building`, `Combat` не переезжали.

## Как устроено сейчас

```text
Assets/
  Prefabs/Characters/Player.prefab
  Resources/
    GameContent/          ассеты предметов, рецептов и каталога
    Placeables/           префабы верстака и стула
  Scenes/
    Game.unity
    HouseInterior.unity
    SampleScene.unity     учебная сцена, в билде включена
  Scripts/
    Building/             установка, контекст локации, мебель
    Camera/
    Combat/               враги. Удар принимается через IImpactReceiver
    Core/                 удар, режим управления, корень связывания
    Crafting/
    Editor/
    Interaction/          контракт получателя и реестр целей
    Inventory/            слоты без сцены и без UI
    Items/                определения, топор, оружие, иконки кодом
    Player/
    UI/                   Canvas, собранный из кода
    World/                комнаты, дом, лес, процедурный арт
  Settings/               URP, Input System
  Welcome/                шаблон Unity, к игре не относится
Docs/
  ARCHITECTURE.md
  PROJECT_STRUCTURE.md
  SYSTEM_DEPENDENCIES.md
  ROADMAP.md
  DECISIONS.md
```

Игровые скрипты лежат в глобальном пространстве имён. Это важно: в ассетах записано `Assembly-CSharp::ItemDefinition`. Пока класс используется сценой или префабом, имя и namespace не меняем.

Смешение, которое не копируем в новые файлы:

- логика топора лежит в `Items`, хотя это презентация руки;
- `LocationContext` лежит в `Building`, хотя это свойство мира;
- спрайты предметов и дома генерируются классами `ItemArt` и `HouseArt`, а не лежат в `Art`.

`Assets/Welcome` и `SampleScene` к игре не относятся. Их не расширяем. Выключение `SampleScene` из билда — отдельное мелкое решение, не часть архитектуры.

Папки `Audio`, `Save` и часть `Art` могут быть пустыми, пока не появится первый файл. Пустую папку в git Unity часто не хранит. Это нормально: папка появляется вместе с первым ассетом, а не заранее десятью заглушками.

Отдельной папки `Scripts/Interfaces` нет. Интерфейс лежит рядом с модулем, который им владеет. `IImpactReceiver` принадлежит Interaction, потому что это контракт удара, а не «вообще интерфейс». Общая свалка интерфейсов быстро перестаёт объяснять, кто имеет право их менять.

Пока новые папки не введены, уже существующие ассеты остаются в `Assets/Resources/GameContent` и `Assets/Resources/Placeables`. Каталог грузится через `Resources.Load`. Перенос в `Assets/Data` делается одним шагом вместе со сменой загрузки, а не копированием. Два каталога сразу заводить нельзя: сегодня `DefaultContent` и ассеты и так дублируют друг друга.

`Resources` после переноса остаётся только для того, что действительно нужно грузить по строке пути. Прямые ссылки в Inspector предпочтительнее.

## Куда класть новый файл

Предмет, который игрок может положить в сумку: ассет в `Data/Items`, регистрация в каталоге. Если он ставится в мир — префаб в `Prefabs/Placeables` и ссылка из профиля. Если он рубит или бьёт — поля `ToolProfile` на том же ассете и, только при новом жесте, префаб презентации в `Prefabs/Player`.

Новый разрушаемый объект мира, который не является предметом: префаб в `Prefabs/World` с `Destructible` и материалом из `Data/Materials`.

Новый рецепт: ассет в `Data/Recipes` и строка каталога. Скрипт крафта не открываем.

Новая локация: `LocationDefinition` в `Data/Locations`. Если ей нужна своя сцена, сцена лежит в `Scenes`, а соответствие «определение → сцена» записывает только `LocationFlow`.

Новый скрипт: в папку модуля, который владеет правилом. Презентация взмаха — `Player`. Приём удара — `Interaction` для интерфейса и компонент на объекте мира. Не создаём `Scripts/Managers`.

Временный отладочный вид, как кнопка спавна слайма, живёт в `UI` и не обрастает собственным статическим протоколом. Когда отладка не нужна, файл удаляется, а не становится системой.

## Правила имён

- Класс и файл называются одинаково, как требует Unity.
- Определение данных заканчивается на `Definition`: `ItemDefinition`, `MaterialDefinition`.
- Профиль, вложенный в предмет, заканчивается на `Profile`: `ToolProfile`.
- Компонент мира называется по обязанности: `Destructible`, `LootDropper`, `WorldDropper`.
- Не называем типы `Manager`, если это не единственный корень. `GameRoot` — исключение с понятной должностью. `InventoryManager` и `ToolManager` не появляются.
- Идентификаторы контента — строчные английские через точку при необходимости: `axe`, `chop`, `recipe.chair`, `workbench`. Имя для игрока живёт отдельно в полях `displayName`.

Новые классы можно объявлять в namespace `Game.<Модуль>`. Старые классы остаются без namespace до отдельного этапа, где мы сознательно обновляем сериализованные ссылки. Смешивать в одном переносе «переехал файл» и «появился namespace» не стоит: по diff будет непонятно, что сломало префаб.

## Что остаётся на своих местах до своего этапа

| Сейчас | Когда переезжает |
| --- | --- |
| `Scripts/Items/Axe.cs` | Вместе с срезом удара, логически становится презентацией в `Player`. Файл можно не двигать, пока класс жив |
| `Scripts/Items/Weapon.cs`, `HeldBow`, `LevitatingSword` | Этап боя, не раньше |
| `Scripts/Combat/IDamageable.cs` | Удаляется после перехода на `IImpactReceiver`, а не переносится |
| `Scripts/Building/LocationContext.cs` | Может переехать в `World` вместе с локациями. До этого не трогаем: на нём висят комнаты |
| `Resources/GameContent` | Один шаг переноса каталога, после того как предметы перестанут собираться из `DefaultContent` |
| Canvas внутри `InventoryHud` | Поздний этап UI |

Физический перенос ради красоты дерева до этапа, который и так меняет модуль, не делаем. Каждый такой перенос шумит в истории и легко роняет ссылку, если забыть `.meta`.
